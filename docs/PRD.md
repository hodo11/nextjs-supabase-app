# 모임 이벤트 관리 웹 MVP PRD

> 한 줄 포지셔닝: "링크 하나로 끝나는 모임 운영 도구"

## 1. 문제 정의

**목적**: 수영·헬스·친구 모임의 주최자가 카톡방과 엑셀에 흩어 처리하던 공지, 참석 확인, 정산, 카풀, 출석 관리를 한 곳에서 처리한다.
**타깃 사용자**: 정기 모임과 일회성 모임을 함께 운영하는 주최자와, 카톡 링크로 들어오는 참여자(범용).

| 주체   | 현재 고통                                            | MVP가 주는 가치                       |
| ------ | ---------------------------------------------------- | ------------------------------------- |
| 주최자 | 참석 인원 취합, 돈 걷기, 카풀 짝짓기를 수동으로 처리 | 링크 하나로 모집, 집계, 정산을 자동화 |
| 참여자 | 카톡방에서 공지와 정산 요청이 묻힘                   | 모임 페이지 하나에서 내 할 일 확인    |

## 2. 사용자와 역할

역할은 **모임(group) 단위**로 부여한다. 같은 사용자가 모임 A에서는 주최자, 모임 B에서는 참여자일 수 있다.

| 역할   | 식별자   | 권한                                                                                          |
| ------ | -------- | --------------------------------------------------------------------------------------------- |
| 주최자 | `host`   | 모임 수정, 초대 코드 재발급, 멤버 권한 부여·제거, 이벤트·공지·정산 관리, 출석 체크, 탑승 승인 |
| 참여자 | `member` | 모임·이벤트 조회, 본인 RSVP 변경, 본인 정산 납부 표시, 운전자 등록, 탑승 신청                 |

- 모임을 만든 사용자는 `groups.owner_id`이자 첫 `host`이다. 주최자는 여러 명일 수 있다(`group_members.role`).
- 모임의 마지막 주최자는 강등·탈퇴할 수 없다.

## 3. 핵심 흐름

1. **주최자 시작**: Google 로그인 → 모임 생성 → 이벤트 생성 → 초대 링크를 카톡으로 공유.
2. **참여자 응답**: 초대 링크 접속 → (비로그인이면) Google 로그인 → 모임 자동 가입 → 이벤트 상세에서 참석/불참/미정 응답.
3. **정산(M2)**: 이벤트 종료 후 주최자가 총비용과 계좌 정보 입력 → 참석자 기준 N빵 금액 계산 → 정산 요청 이메일 발송 → 참여자가 송금 후 "송금했어요" 표시 → 주최자가 입금 확인 체크.
4. **카풀(M3)**: 운전자가 출발지·시간·좌석 수 등록 → 참여자가 탑승 신청 → 운전자 또는 주최자가 승인.
5. **출석(M4)**: 주최자가 이벤트 후 출석 체크 → 멤버별 출석률 조회.

```
[초대 링크 /invite/[code]]
   ↓ 비로그인 → 로그인 페이지 (next 파라미터로 원래 링크 보존)
   ↓ 로그인 완료 → 초대 수락 페이지
   ↓ 자동 가입 (이미 멤버면 가입 생략)
[모임 상세 페이지] → [이벤트 상세 페이지] → RSVP 응답
                                         ├→ (M2) 정산 영역
                                         ├→ (M3) 카풀 영역
                                         └→ (M4) 출석 영역 (주최자)
```

분기점:

- 초대 코드 무효(재발급됨): 오류 안내 후 홈으로 이동.
- 정원 초과 상태에서 "참석" 선택: 대기자로 등록되고 안내 문구 표시.
- 응답 마감 이후: RSVP 변경 불가(주최자는 수동 변경 가능).

## 4. 기능 명세

우선순위: **P0** 없으면 출시 불가 / **P1** 해당 마일스톤 목표에 필요 / **P2** 여력 시 포함.

| 출석 현황 페이지     | 멤버별 출석률 조회      | 모임 상세의 "출석 현황" 탭                | 멤버별 출석률 확인                                    | 출석 횟수·출석률 표                                                      | F017                                     |

정합성 확인: F001~F017이 모두 한 곳 이상의 페이지에 배치되어 있고, 위 모든 메뉴·페이지는 기능 명세의 관련 페이지와 일치한다. 정산·카풀·출석은 별도 메뉴 없이 이벤트 상세 페이지(및 정산 페이지)에서 진입한다.

### 기존 코드와의 연계

- **공개 경로**: 초대 링크 경로 `/invite/[code]`는 `lib/supabase/proxy.ts`의 `updateSession()` 공개 경로 조건에 `startsWith("/invite")`를 추가해야 한다(`proxy.ts` 루트 파일이 아니라 이 함수의 조건문). 페이지 내부에서 세션을 확인해 비로그인이면 `/auth/login?next=/invite/[code]`로 보낸다.
- **로그인 복귀**: 현재 `app/auth/*` 로그인 흐름은 `next`를 처리하지 않는다면 OAuth 콜백(`app/auth/confirm/route.ts` 및 Google 콜백)에서 `next`를 보존하도록 보완한다(F001). 외부 URL로의 오픈 리디렉션을 막기 위해 `/`로 시작하는 내부 경로만 허용한다.
- **프로필**: 기존 `profiles` 테이블(`auth.users`와 1:1)을 멤버 이름·이메일 표시에 재사용한다. 같은 모임 멤버가 서로의 프로필 이름을 볼 수 있도록 `profiles` select 정책을 확장해야 한다.
- **Supabase 클라이언트**: 서버 컴포넌트·Server Action은 `lib/supabase/server.ts`, 클라이언트 컴포넌트는 `lib/supabase/client.ts`를 사용한다.

## 6. 데이터 모델

모든 테이블에 RLS를 적용한다. 규칙: **같은 모임 멤버만 조회, 쓰기는 본인 행 또는 주최자만 허용**. 정책의 멤버십 확인은 `security definer` 헬퍼 함수(`is_group_member`, `is_group_host`, `set search_path = ''`)로 구현해 정책 간 재귀를 피한다. 마이그레이션은 `supabase/migrations/`에 마일스톤별로 추가한다.

## 7. 기술 스택 (현재 저장소 기준)

- **프레임워크**: Next.js 16 App Router, React 19, TypeScript(strict)
- **UI**: Tailwind CSS 3, shadcn/ui(new-york), Lucide React. 모바일 우선 레이아웃(카톡 링크 진입 대응)
- **폼·검증**: React Hook Form, Zod
- **백엔드**: Supabase(Auth, Postgres, RLS). 데이터 변경은 Server Action, 조회는 서버 컴포넌트에서 수행
- **이메일**: Resend 등 외부 서비스를 Route Handler 또는 Supabase Edge Function에서 호출. 리마인드는 Supabase Cron(`pg_cron`)
- **배포**: Vercel
- **구조**: 루트 `app/`, `components/`, `lib/` 사용(`src/` 없음), 경로 별칭 `@/*`
